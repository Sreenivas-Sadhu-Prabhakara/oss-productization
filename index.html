The method

Productizing OSS is a brownfield problem you don't own.

The system already exists — but it's someone else's code. So you never strangler-rewrite it. You pin a release, read its license as a load-bearing constraint, and build a separate value layer alongside it. The plan is mostly KEEP (upstream, untouched) + ADD (your wedge).

M1 · Managed host

Run upstream ≈unmodified as a service — deploy, backups, SLA, support. Gated by copyleft & branding terms.

M2 · Vertical SaaS

Upstream engine + a domain skin and one killer workflow. Needs a permissive license to own-brand.

M3 · Wedge-on-top

A separate layer (provisioning, ops, data) that calls upstream but isn't a derivative. Any license.

  1. Capture the upstream: pin a release, read the LICENSE, map the API you'll build against.
  2. Plan the diff: KEEP upstream + ADD the wedge; a license breach is rejected before you build.
  3. Build the wedge only — the upstream stays a pinned dependency, never a fork.
  4. Ship to an MVP bar: runs, access-gated, license-clean, reproducible, honestly described.

How to read this

These are productization guides, not product announcements. Each project's license and pinned version were verified against its repository on 2026-11-23 (read from each LICENSE file and the GitHub release list), and the deploy claims about a self-hosted PaaS are drawn from its public template catalogue. Everything downstream of that — exact stacks, API surfaces, running instances — is a plan, not a demonstration. Nothing here is a live product, and none of these projects endorses this.

The value is the license-first teardown: for seven real, high-adoption projects, here's what you're actually allowed to build on top, and the smallest wedge that turns "the OSS, running" into something you could sell.
