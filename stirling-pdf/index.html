Stirling-PDF productization — a compliance document-ops vertical

Stirling-PDF is a self-hosted toolkit of PDF operations — merge, split, convert, OCR, redact, sign. Productize it as a vertical workflow for regulated back-office work, where the killer feature is redaction you can actually trust.

What it is

A browser-based PDF operations engine.

Stirling-PDF is a Spring Boot web app that exposes dozens of document operations through a UI and a REST API, plus a pipeline feature for chaining them. It leans on heavy external engines — LibreOffice for office conversions, OCRmyPDF/Tesseract for OCR, qpdf/Ghostscript for manipulation — bundled in its official Docker image. The API and pipeline are the surface a product drives headlessly for batch work.

The license reality

MIT at the core — but mind the carve-out.

MIT base + per-directory proprietary dirs

The base license is MIT — rebrand, close your wedge, and run it as a service, all permitted. (Note MIT has no patent grant, unlike Apache-2.0.) But it's open-core: specific directories in the repo — proprietary, SaaS, engine and editor variants — are governed by separate per-directory license files, not MIT.

So the rule is simple: build the vertical on the MIT community core, and don't take a dependency on (or reimplement to undercut) the proprietary directories. Record that boundary in a one-paragraph license posture.

How you'd productize it

One compliance workflow, not a toolbox.

The bare toolkit is a pile of buttons. The product is a single, repeatable vertical flow with a compliance stake — the obvious one for banks, BPOs and legal back-offices:

  • Bulk true-redaction + OCR + packaging: ingest a batch of documents, remove PII, make them searchable, and emit an audit-logged, packaged output.
  • Who pays: regulated back-office and outsourcing teams that process sensitive documents at volume and must prove they did it safely.
  • Why MIT makes it easy: you can present it as your own branded product and keep the workflow layer closed.

The groove

Pin-and-wedge, concretely.

  1. Pin at a release (here, v3.5.0) and stay on the MIT core; note the engine dependencies are heavy, so size the host accordingly.
  2. Deploy on a self-hosted PaaS; access-gate it and process uploads ephemerally — sensitive documents shouldn't persist past the job.
  3. Wrap the workflow over the REST API / pipeline — batch intake → redact → OCR → packaged output — as your own layer.
  4. Gate on redaction integrity (below) before anything ships.

The catch

Redaction is a security test, not a visual one.

A black box is not a redaction

Real redaction must remove the underlying content, not draw a rectangle over it. If the implementation only overlays, the "redacted" text is still recoverable by copy, extract, or re-render — and that's a data breach you shipped. This must be proven with an extract-text test on the output: zero target strings recoverable, or the release is blocked.

Confirm the upstream's redaction mode before promising it; if it overlays, your wedge has to flatten or re-render to genuinely destroy the content. Treat this as the one gate that can stop the whole product.
